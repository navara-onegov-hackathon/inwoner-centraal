# Demo Narrative

## One-line story

When Truus loses her husband, she should not have to become the integration layer between government organisations. Our platform becomes that layer for her.

## Narrative arc

Truus has just lost her husband Cees. Instead of a flood of disconnected letters from RDW, CAK, Toeslagen, SVB, the gemeente, and the waterschap, she gets one place where the government has already assembled what matters.

The platform starts from the death event and delegated authority. It checks which organisations are relevant, retrieves what it can from existing services, and converts fragmented records into one understandable case overview.

For the demo, Truus has chosen the highest service level: handle as much as possible for me.

That means the platform does not wait for her to figure out which letters matter. It proactively:

- identifies what has already been arranged
- flags what still needs attention
- prepares actions where possible
- asks only the questions that truly require her input

The result is a service that feels like one government, even though the underlying systems remain many.

## Core message

This is not an AI chatbot for grief. This is a background intelligence and orchestration layer that reduces burden, assembles fragmented public service information, and lets the government act more like a coordinated whole.

## The problem we show

In the Truus case:

- Cees was registered at a care home
- Truus lives elsewhere
- letters go to different addresses
- some are personal, many are addressed to "de erven van"
- some require no action, others hide urgent obligations
- some arrive within days, others much later

Today, Truus has to interpret that chaos herself.

## The change we demonstrate

With our platform:

- Truus sees a single overview
- the platform explains what is automatic and what is not
- the platform combines digital and paper-originating processes
- the platform asks only minimal follow-up questions
- the platform prepares actions instead of only listing them

## Narrative caveat

The onboarding flow is still work in progress.

For the narrative and pitch, we should describe the intended user journey based on the onboarding direction, not treat the current screens as final UI. In particular:

- the flow starts with a condolence message
- the user chooses who will handle the process
- the user chooses how much the system may do
- the agent starts gathering relevant information
- gathered information is shown back for verification and correction
- after that, the user lands in the case overview and process screens

## Demo flow

### 1. Start with a condolence message

The first screen is not a task board. It starts calmly, from Truus's perspective.

The message is essentially:

"We leven met u mee. In deze periode helpen we u begrijpen wat de overheid regelt, wat nog aandacht vraagt, en wat we al op de achtergrond voor u kunnen doen."

This sets the tone: calm, supportive, and not bureaucratic.

### 2. Let the user choose who handles the process

The next decision is about control and delegation.

Truus chooses between:

- managing it herself
- letting someone else manage it
- doing it together

If someone else takes over, we use DigiD machtigingen. In that route, we do not keep asking Truus follow-up questions. We go straight toward a single overview for the delegated person, because the point is to reduce burden immediately.

For the current demo build, this delegation flow is still being refined, but the narrative should reflect this intended direction.

### 3. Let the user choose how much the system should do

Only if Truus continues herself, or together with someone else, do we ask the next question: how much may the system handle?

This is the role of the begeleiding step:

- handle as much as possible for me
- I prefer to do it myself
- I choose per organisation

This choice is important because it changes the whole experience:

- how many actions the user sees
- what agents do in the background
- where confirmation is still needed

### 4. Show the agent getting to work

After that choice, the platform begins working on Truus's behalf.

This is where we demonstrate orchestration:

- determine which organisations are relevant for this person
- gather data from connected sources
- combine records from APIs, agent-to-agent connections, and other channels
- infer which processes, obligations, and rights actually apply

The screen that visualizes this work will still change, so in the narrative we should focus on the behavior, not on the exact current layout.

### 5. Show gathered information and allow corrections

Once information is assembled, the platform shows what it found and asks the user to verify or correct it if needed.

Examples:

- address
- BSN
- IBAN
- other case-relevant data that may differ between organisations

The important product point is that these forms will ultimately be generated by `ag-ui`. Today some of this is still hardcoded, but the narrative should describe the intended generated-form workflow.

### 6. Move into the case overview

From there, the user arrives at the main case experience:

- an overview of processes, grouped in tabs
- a screen that shows the current situation and the new situation
- the options available to the user, for example requesting subsidies or other arrangements

This is where the platform makes the fragmented process understandable as one coherent journey.

### 7. End on peace of mind

Close on the emotional outcome, not just the workflow outcome.

Truus no longer has to decode six organisations by herself. She sees one overview, understands what is changing, and only gets involved where her judgment or approval is actually needed.

## What makes this compelling to the jury

- It is clearly useful to the bereaved partner.
- It links multiple organisations.
- It is proactive.
- It respects existing government infrastructure instead of replacing everything.
- It uses AI where it adds leverage, but keeps the user experience calm and practical.

## Suggested spoken pitch track

Truus has just lost her husband. Today, that means grief plus an administrative storm: letters to the wrong address, unclear obligations, and no single place to understand what is happening.

Our solution starts differently. First, Truus gets a condolence message and one calm entry point. Then she decides who will handle the process: herself, someone else, or together. If someone else takes over, we use DigiD machtigingen so that person can continue without Truus carrying the burden.

If Truus continues, she then chooses how much the system may do: as much as possible, everything herself, or a split per organisation. Based on that choice, the agent starts working in the background. It determines which organisations are relevant, gathers data from sources, and builds up the processes that matter in this specific case.

Before moving on, the platform shows the gathered information back to the user so she can correct it where needed. Those forms are intended to be generated dynamically, even if parts are still work in progress today.

From there, she arrives at one overview of processes in tabs, plus screens that explain the current situation, the new situation, and the options she has, such as requesting applicable support. So the innovation is not an AI chat window. The innovation is that Truus no longer has to act as the integration layer between government organisations.
